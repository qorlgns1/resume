## 권장 작업 순서

1. **저장 계층과 인증**
   - DB와 인증을 정하고, 어드민 변경 API의 경계(`/api/admin/*`)를 정합니다.
   - 공개 API(`/api/public/v1/*`)는 게시된 버전만 읽도록 바꿉니다.
2. **초안 · 게시 · 버전**
   - `SiteDocument` 단위로 `Draft`와 `PublishedVersion`을 저장합니다 (`packages/contracts/src/versioning.ts`).
   - 게시하면 버전 번호가 늘고, 복원은 이전 버전으로 새 초안을 만듭니다.
   - 공개 사이트 캐시 무효화(재검증 웹훅 또는 `revalidateTag`)를 설계합니다.
3. **편집 UI**
   - 설정 패널의 읽기 전용 필드를 폼으로 바꿉니다 (contracts 스키마로 검증).
   - 원본 콘텐츠(프로필·프로젝트 등) 편집 화면과 모듈 인스턴스 설정을 구분합니다.
   - 모듈 추가·삭제 후, 12칼럼 이동·크기 변경, 모바일 순서·너비·숨김 순으로 진행합니다.
   - 저장 성공은 실제 저장 응답을 받은 뒤에만 표시합니다.
4. **페이지**
   - 개인 프로젝트: 목록 → `/projects/[slug]` 상세 (고정 메타데이터 + 블록 본문)
   - 회사 경험: 회사별 목록 → 상세
   - 히스토리: 챕터(기본 2개) + 타임라인, 회사·프로젝트 연결 또는 직접 작성
   - 사용자 페이지 추가: `kind: "custom"`, slug 라우팅
5. **미디어**: 업로드, 이미지 최적화(`next/image` 원격 패턴), placeholder 대체
6. **운영 준비**: CI(lint, typecheck, build, smoke), 에러 로깅, 보안 헤더, 백업

## 알려진 제약

- 공개 페이지는 요청마다 렌더링합니다 (`connection()`). 게시 흐름이 생기면 캐시 전략을 정합니다.
- 공개 API 응답의 `content`에는 전체 라이브러리가 들어 있습니다. 게시 구조를 정할 때 페이지가 참조하는 항목만 담도록 줄일 수 있습니다.
- 모바일 `custom` 순서는 CSS `order`를 쓰므로 스크린 리더의 읽기 순서와 다를 수 있습니다.
- 어드민은 1100px 이상 데스크톱 화면을 기준으로 만들었습니다.
- 스모크 테스트는 31xx 포트를 사용합니다. 그 포트가 이미 쓰이고 있으면 실패합니다.
- Docker 이미지는 Node 24 alpine 기준이며, 크기는 약 300MB입니다 (최적화 전).
